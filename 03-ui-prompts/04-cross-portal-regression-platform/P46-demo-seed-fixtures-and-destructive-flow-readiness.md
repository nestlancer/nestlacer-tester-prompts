# P46 — Demo seed fixtures, audit records and destructive-flow readiness

**Priority:** P0  
**Primary role:** Test data steward + QA operator  
**Scope:** Prove the production-like environment has enough demo/audit data to execute all prompt flows, including destructive create/update/delete/status/password/session/payment/media/webhook operations.
**Target host:** `https://nestlancer.com` + `https://app.nestlancer.com` + `https://admin.nestlancer.com`
**Accounts:** see [`DEMO-ACCOUNTS.md`](../../00-start-here/DEMO-ACCOUNTS.md)

## Tooling (required)

- **Frontend pages / UI walks:** use **Playwright CLI** only (`npx playwright`, `playwright test`, or short Playwright CLI scripts). Drive navigation, forms, screenshots, console, and network from Playwright.
- **Direct API / gateway endpoints:** use **`curl`** against `https://api.nestlancer.com/api/v1` (or same-origin `{portal}/api/v1/*` for BFF/cookie checks when an API cross-check is needed). Record method, path, status, and redacted headers/body keys.
- **Do not use** Cursor browser MCP, Chrome DevTools MCP, browser-use agents, or other heavy interactive browser MCP stacks for this suite.

## 0. Demo-production mode for this prompt

The product owner confirmed this is a production application with demo data. Therefore this prompt must not avoid destructive operations merely because they mutate data. Instead, first prove the target object is demo/audit/test data, then execute the destructive check, then verify the after state and audit trail.

## 2. Fixture categories that must exist

Use [`DEMO-ACCOUNTS.md`](../../00-start-here/DEMO-ACCOUNTS.md) for logins. Prefer existing seeded clients (15) + catalog; create `AUDIT-*` records for missing destructive cohorts.

- Admin/operator: `admin@nestlancer.com` (+ disposable AUDIT operator if password/session tests would damage shared admin).
- Client demo accounts (15 named `@nestlancer.com` clients). For IDOR use two distinct clients. Cohorts not present in seed (unverified / 2FA / suspended) → create via UI/API as AUDIT-* or mark that branch BLOCKED.
- Contact inquiries in new/contacted/resolved/spam-like states (create AUDIT-* if missing).
- Requests / quotes / projects / payments covering major statuses — use seeded scenario projects first, then AUDIT-* for gaps.
- Media / messages / notifications / content / system templates — verify via admin UI or API gateway lists.
- Integrations/webhooks: operator-approved **public HTTPS** demo sink only (never localhost).
- Worker/outbox/audit rows generated by safe demo actions visible through admin/API where exposed.

**Public-domain note:** seed-script execution, DB/MinIO/Redis shells, and `--confirm-prod` reset are **operator-only**. External LLM runs prove readiness via HTTPS portals + `https://api.nestlancer.com/api/v1`.

## 3. What this prompt must prove

- Every prompt P01–P47 and A01–A20 has a fixture path: existing seed record, record created during the prompt, or explicitly blocked due to missing environment capability.
- Demo/audit records are identifiable in the UI/API before mutation, using name/email/slug/prefix/metadata such as `AUDIT-<PROMPT-ID>-<YYYYMMDD>-<n>`.
- Destructive operations produce reversible or acceptable demo-only outcomes and do not touch real records.
- Seeded catalog expectations are met: public content, templates, feature flags, notification templates, quote blocks, service package and platform payment accounts are present.
- Cache busting/reseed guidance exists when public pages show stale empty data.

## 4. Mandatory readiness checks

1. Create a fixture ledger mapping each prompt to required accounts/records and identify the exact demo record(s) used.
2. Confirm seeded catalog counts where accessible:
   - Blog categories/tags/posts
   - Portfolio categories/items
   - Email templates
   - Feature flags
   - Notification templates
   - Quote blocks
   - Service package(s)
   - Platform payment accounts
3. Create fresh audit records for prompt execution using naming prefix `AUDIT-<PROMPT-ID>-<YYYYMMDD>-<n>`.
4. Run one full sacrificial destructive cycle for each class on demo data:
   - create → edit → status change → archive/restore/delete if available
   - user password reset/set password/session revoke on a disposable user
   - payment manual/offline/refund/dispute/reconciliation on a test-mode demo payment
   - media upload/share/revoke/move/quarantine/delete on a disposable file
   - webhook integration enable/disable/test/delete on a demo sink
   - notification template/broadcast to demo recipient only
5. Verify after-state in UI, direct linked pages, audit logs, notifications/outbox and any cross-portal view.
6. If a fixture is missing, create it through the app UI whenever possible, otherwise record exact API/seed step needed and mark only that prompt section BLOCKED.
7. Verify stale cache handling: if public blog/portfolio/marketing content is empty after seed, document cache-bust step rather than treating it as content absence.
8. Confirm that production seed safeguards are understood: `--env=prod` rejects reset/demo unless explicitly confirmed; never use reset unless it is the explicit test goal.

## 5. Negative and edge probes

- Attempt to mutate a non-demo-looking record and verify the tester stops before confirmation.
- Try to reuse an audit slug/name/email and verify idempotent behavior or clear duplicate validation.
- Use records in boundary states: archived/completed/refunded/disputed/inactive/suspended.
- Verify destructive controls include specific confirmation copy and do not accidentally act on all records.
- Check whether list counts, dashboards and public pages update or need cache invalidation after mutations.

## 6. Data and safety fences

- Destructive actions are allowed only after proving the record is demo/audit/test data.
- Never reset/wipe a live database unless an authorized operator explicitly requests a destructive environment reset.
- Never expose seed secrets beyond the known demo password documented in DEMO-ACCOUNTS.md; never paste tokens/cookies/OTPs/reset links into reports.
- Real external notifications/webhooks/payments remain forbidden unless explicitly approved for a demo sink.

## 7. Required evidence

- Fixture ledger with account/record IDs redacted or partially masked where needed.
- Screenshots before/after destructive cycles.
- Network rows and audit-log entries for every destructive action.
- Seed/catalog count snapshot and cache-bust notes.
- List of missing fixtures and how to create them.

## 8. Defects this prompt is designed to catch

- Prompt suite blocked because fixtures do not exist.
- Testers refusing to execute required destructive flows despite demo data approval.
- Destructive controls acting on non-demo records or bulk scope unintentionally.
- Missing seed catalog/template/payment/legal data.
- Stale public cache hiding seeded content.
- Demo accounts unable to traverse role/status/payment/session branches.

## Security addendum — mandatory for this prompt

Run the relevant checks from [`00-SECURITY-RUNBOOK.md`](../../06-security-prompts/00-SECURITY-RUNBOOK.md) before closing this prompt.

At minimum, while executing this UI prompt verify:
- Protected UI/API calls are not accessible anonymously or by the wrong role.
- Demo user A cannot view or mutate demo user B objects by changing IDs, URLs, filters or request bodies.
- All text/query/file/template fields safely handle malicious-looking input without XSS, open redirect, path traversal, stack traces or debug leakage.
- Mutating controls are resistant to CSRF/clickjacking assumptions and have correct confirmation/audit behavior.
- Browser storage, console output, debug panels, generated artifacts and network responses do not leak tokens, cookies, OTPs, reset links, private URLs, provider secrets or unnecessary PII.
- If this prompt touches payments, webhooks, media, documents, messaging, notifications, exports or system operations, also run the matching `S##` security prompt from `06-security-prompts/`.

Add a `Security findings` section to the prompt result using the security runbook output template. Stop and escalate P0 for auth bypass, cross-user data, token leakage, stored XSS, duplicate charge, unsigned webhook acceptance, unsafe webhook target acceptance or impersonation attribution failure.
